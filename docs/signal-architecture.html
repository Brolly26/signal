Signal — how an analysis actually runs

The implemented path, in execution order. Follow the numbers.

  1. 1
    The browser posts the request HTTP/JSON. No key and no database credential ever reaches the browser.
  2. 2
    The request is saved first Committed before any model call, so an AI failure never costs a submission.
  3. 3
    The model is called System prompt, one strict tool, and a JSON schema. The customer's text goes in as untrusted data.
  4. 4
    The model asks to search It chooses the query itself — often for the underlying need, not the customer's words.
  5. 5
    The tool runs SELECT only Capped at 8 rows, and the analysed request is always excluded. Read-only by construction.
  6. 6
    Results go back, and it may search again Steps 4–6 repeat inside the budget: 3 iterations, 4 tool calls.
  7. 7
    The final JSON hits the validation gate Every id is checked against the ids the search actually returned. All invalid → the analysis fails rather than showing a confident answer.
  8. 8
    The analysis is stored With its candidates and the evidence for each. A foreign key blocks any reference to a request that does not exist.
  9. 9
    A human approves or rejects Only this creates a link. It never merges or deletes the originals, and the decision log is append-only.

What the diagram is claiming

  • The model is offered exactly one tool, and that tool only runs SELECT.
  • There is no path from the model to a write. It cannot create, merge or delete anything.
  • The request-level classification is derived at step 7, not taken from the model.
  • Every guarantee above is also enforced by a database constraint, not only by application code.
