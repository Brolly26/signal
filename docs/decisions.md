# Architectural Decisions

Each entry records what was chosen, why, what else was considered, and what the
decision costs. Corrections to earlier claims are kept visible rather than
quietly edited out.

---

## ADR-001 — Two services: Next.js frontend, FastAPI backend

**Decision.** The frontend is a Next.js application; all business logic, data
access and LLM orchestration live in a Python FastAPI service.

**Why.** The AI layer is the substance of this project: structured output
validation, tool execution, reference checking and failure handling. Putting it
in Python with Pydantic makes those guarantees explicit and testable.

**Alternative considered.** A single Next.js application with route handlers.
That is genuinely simpler — one process, one language, no CORS, no duplicated
types at the boundary.

**Cost accepted.** Two processes to run, a serialisation boundary, and request
and response shapes defined twice (Pydantic models and TypeScript types) with no
compiler enforcing that they agree. Mitigated by keeping the API surface small
and typed on both sides.

## ADR-002 — Plain SQL migrations and asyncpg, no ORM

**Decision.** Schema changes are versioned `.sql` files applied by
`scripts/migrate.py`, which records each file with a checksum in
`schema_migrations`. Queries are written directly against asyncpg.

**Why.** The schema is six tables, and its interesting parts are constraints,
partial indexes and full-text search — things an ORM hides. The queries that
matter (`ts_rank` ranking, lateral joins to the latest analysis) would be
hand-written SQL in any case.

**Alternative considered.** SQLAlchemy plus Alembic. It would give
autogenerated migrations and a session abstraction.

**Cost accepted.** No automatic migration generation, no lazy relationship
loading, and SQL duplicated across repository functions if we are careless. The
checksum guard in the migration runner replaces the safety an ORM's migration
history would provide: an already-applied file cannot be edited silently.

## ADR-003 — Supabase Postgres, with local Docker parity

**Decision.** `DATABASE_URL` points at either a Supabase project or the local
`docker compose` Postgres. The same migrations run unchanged against both. The
Supabase client libraries and PostgREST are not used.

**Why.** The brief asks for Supabase; the assessment also has to be
reproducible by someone who clones the repository and has no access to our
project. Connecting to Supabase's Postgres over a standard connection string
satisfies both.

**Cost accepted.** We give up Supabase-specific features — Row Level Security,
the auto-generated REST API, the JS client. None of them would be used anyway,
because all authorisation decisions belong in the backend.

**Operational note.** Supabase's pooler (port 6543) runs pgbouncer in
transaction mode, which is incompatible with asyncpg's prepared-statement cache.
Use the direct connection on port 5432, or set `DB_STATEMENT_CACHE_SIZE=0`.
`scripts/migrate.py` always connects with the cache disabled so it works either
way.

## ADR-004 — LLM tool calling: our choice, not a requirement

**Correction.** An earlier version of the plan stated that real LLM tool calling
is an explicit requirement of the Metacto brief, and that backend-managed
retrieval could only search on the user's literal words. **Both statements were
wrong.**

* The brief asks for real LLM tool invocation *when tool calling is
  implemented*, and explicitly permits backend-managed retrieval provided the
  architectural trade-off is documented. Implementing it is our decision.
* A backend-orchestrated pipeline can reformulate queries just as well: call the
  model once to extract the underlying need and emit search terms, run those
  searches in the backend, then call the model again to compare candidates. That
  reaches the same retrieval quality.

**Decision.** Implement tool calling, with the deterministic pipeline retained
as the fallback path.

**Why.** The real difference is not retrieval quality, it is *who decides at
runtime how many searches to run and with what terms*:

| | Backend-orchestrated (2 calls) | Tool calling (bounded loop) |
|---|---|---|
| Search strategy | fixed at design time | chosen per run by the model |
| Can react to what the first search returned | no | yes |
| LLM calls per analysis | exactly 2 | 2–4 |
| Determinism and testability | high | lower |
| Latency and token cost | lower | higher |

The adaptive behaviour is a real capability, but on a small dataset the gain is
modest and we will not claim otherwise.

**How this gets settled.** The deterministic path has to exist regardless, as
the fallback for when the model does not call the tool — and that fallback *is*
the two-call pipeline. `ai_analyses.retrieval_mode` records which path produced
each analysis (`agentic` or `backend_fallback`), and the evaluation suite runs
the same labelled cases through both, comparing duplicate precision, call count
and latency. If the deterministic path matches the agentic one, that result is
recorded here.

**Cost accepted.** Non-determinism, higher latency and cost, and the need for a
reference allowlist, a tool-call budget and a fallback path.

## ADR-005 — Forced tool choice is unavailable; structured output instead

**Decision.** The tool is offered with `tool_choice: auto`, `strict: true`, and
a prompt instruction naming it. The analysis JSON is constrained with
`output_config.format` and then validated again with Pydantic.

**Why.** Current Anthropic models reject forced tool choice:
`tool_choice: {"type": "tool", ...}` and `{"type": "any"}` return HTTP 400 on
Claude Sonnet 5.5 and Claude Opus 5.5. Verified against the installed SDK:
`ToolChoiceToolParam` still exists in `anthropic` 1.15.0, so the SDK accepts the
parameter and the rejection happens server-side at request time. The design has
to respect the restriction; the SDK will not warn us.

**Cost accepted.** We cannot guarantee the model calls the tool, which is
exactly why the fallback in ADR-004 is mandatory rather than optional.

## ADR-006 — The request-level classification is derived, not model-emitted

**Decision.** Two separate levels:

* **Per candidate** — `analysis_related_requests.relationship_type`
  (`DUPLICATE` or `RELATED`) with its own `explanation`. This is what a product
  manager approves or rejects, one candidate at a time.
* **Per request** — `ai_analyses.classification` (`DUPLICATE`, `RELATED`,
  `DISTINCT`, `NEEDS_CLARIFICATION`), the headline shown on the board and in the
  review queue.

The model emits only the per-candidate relationships and a
`needs_clarification` flag. The backend derives the aggregate:

```
needs_clarification                      -> NEEDS_CLARIFICATION
any validated candidate is DUPLICATE     -> DUPLICATE
any validated candidate is RELATED       -> RELATED
model cited no candidates at all         -> DISTINCT
```

**Why.** If the model emitted both levels it could return `DISTINCT` while
listing a duplicate — a contradiction the backend would have to resolve anyway.
Deriving the aggregate removes the whole class of inconsistency and makes the
rule unit-testable without an LLM.

**Cost accepted.** We lose the model's own global opinion as an independent
signal. The per-candidate view is more actionable and is what a human reviews.

## ADR-007 — All references invalid is a failure, not a DISTINCT verdict

**Decision.** Every `related_request_id` the model returns is checked against an
allowlist of the ids that the search tool actually returned during that run, and
against the analysed request's own id. Then:

| Model output | Result |
|---|---|
| cited no candidates | `completed`, classification `DISTINCT` |
| cited candidates, some valid | `completed`, classified from the valid ones, `fabricated_refs_count` recorded |
| cited candidates, **all invalid** | `failed`, `error_code = FABRICATED_REFERENCES` |

**Why.** "The model found nothing related" and "the model produced references we
could not verify" are different events. Collapsing the second into `DISTINCT`
would present a validation failure as a confident verdict, and would hide it
from the retry path. As a failure it stays visible and re-runnable.

**Cost accepted.** A request can end up with no analysis until someone retries
it. That is the honest state, and the retry endpoint exists for it.

## ADR-008 — Append-only decisions, separate from approved links

**Decision.** `review_decisions` is an append-only audit log — rows are never
updated or deleted. `request_links` holds the current human-approved state. The
effective decision for a pair is its most recent row.

When a decision changes, in one transaction:

| Action | Effect on `request_links` |
|---|---|
| `APPROVED` | insert the normalised pair, `ON CONFLICT ... DO UPDATE SET link_type` |
| `REJECTED` | delete the link **only if** no other analysis currently has an effective `APPROVED` decision for the same pair |
| `APPROVED` after `REJECTED` | re-insert; idempotent |

**Why.** The conditional delete prevents a real bug: if one reviewer approved
A↔B through analysis 1 and another rejects the same pair through analysis 2, the
rejection must not silently remove a link somebody else approved.

Approving a duplicate never deletes or merges the original requests. It inserts
a link and sets the request's status to `triaged` — a signal, not destruction.

**Cost accepted.** Reading the current state costs a query over the decision log
instead of a single column lookup.

## ADR-009 — Concurrency and interruption recovery at the database level

**Decision.** A partial unique index,
`ai_analyses_one_pending_per_request ON ai_analyses (request_id) WHERE status = 'pending'`,
allows at most one in-flight analysis per request. There is no application lock.

Two interruption shapes are recovered, and they are distinct:

* the worker **started and hung** — `started_at` is older than
  `STALE_ANALYSIS_STARTED_SECONDS`
* the worker **never started** — `started_at IS NULL` and the row has been
  sitting since `created_at`, older than
  `STALE_ANALYSIS_NEVER_STARTED_SECONDS` (the process died between inserting the
  row and picking up the background task)

Both are released as `failed / INTERRUPTED`, which makes them visibly
retryable. Release happens in the startup sweep and, per request, inside the
retry transaction: stale rows are released and the new analysis is inserted
atomically, so if a genuinely fresh analysis is still running the insert raises
a unique violation and the release rolls back with it. The API maps that to
HTTP 409.

The worker's own writes are conditional (`WHERE id = $1 AND status = 'pending'`)
so a late-waking worker cannot overwrite a row that was already failed or
completed.

**Alternative considered.** A real job queue (Celery or RQ with Redis), which
would bring retries, visibility and worker supervision.

**Cost accepted.** `BackgroundTasks` runs in the API process, so analyses do not
survive a restart — they are recovered as failures, not resumed. A queue is the
correct next step for production and is documented as such, not implemented.

## ADR-010 — Claude Sonnet 5.5 as the default model

**Decision.** `LLM_MODEL=claude-sonnet-5-5`, configurable by environment
variable. Pricing at the time of writing: $2/$10 per million input/output
tokens, against $4/$20 for Claude Opus 5.5.

**Why.** The task is comparison and classification over short texts, not
long-horizon reasoning. Starting at the cheaper model and escalating only on
evidence is the right order.

**Model-specific behaviour that affects the code.** On Sonnet 5.5,
`thinking: {"type": "disabled"}` returns 400 (we use the adaptive default),
`effort` defaults to `high` so we set it explicitly, and forced tool choice is
rejected (see ADR-005).

**How a change would be justified.** The evaluation suite records per-analysis
latency and token cost alongside classification accuracy. A recommendation to
move to Opus would come from those measurements, not from preference.

## ADR-011 — Metrics separate automatic processing from human decision time

**Decision.** Three distinct intervals, each derived from stored timestamps:

| Metric | Measured as | What it reflects |
|---|---|---|
| AI processing time | `ai_analyses.started_at` → `completed_at` | the automated step alone |
| Queue wait | `ai_analyses.created_at` → `started_at` | backlog before work begins |
| Time to human decision | `ai_analyses.completed_at` → first `review_decisions.created_at` | reviewer responsiveness |

Triage time, the business metric, is submission to human decision — the sum of
all three. It is reported as a composition, never as a single number that
implies the AI took that long.

**Why.** Mixing them would let a fast model hide a slow review queue, or make a
reviewer's lunch break look like model latency. The two have different owners
and different fixes.

**What we will not claim.** No business improvement figure without data from
real users. The precision numbers from the evaluation suite are reported with
the sample size next to them and labelled as regression measurements, not
production accuracy.

## ADR-012 — Next.js 16.4.2, verified before adoption

**Decision.** `next@16.4.2` with React 19.3.0, Tailwind CSS 4 and TypeScript 5.

**Verification performed.** `next@16` declares `node >=20.9.0` (local Node is
24.12.0) and peer React `^18.2.0 || ^19.0.0`. After scaffolding,
`npx tsc --noEmit` exits 0 and `npm run build` compiles and prerenders
successfully. Note that npm exposes no `lts` dist-tag for `next`; `16.4.2` is
the current `latest` and the current major line.

**Known accepted issue.** `npm audit` reports five high-severity advisories, all
in the lint toolchain: `eslint-config-next` → `@next/eslint-plugin-next` →
`fast-glob` → `micromatch` → `braces`. Runtime dependencies are only `next`,
`react` and `react-dom`; the affected packages are devDependencies and ship
nothing to the browser or server. `npm audit fix` does not resolve them and
`npm audit fix --force` would break `eslint-config-next`. Documented and
accepted rather than papered over.

## ADR-013 — The optional clarification question is deferred

**Decision.** The clarification question is not built until the required
workflow is complete and tested. `NEEDS_CLARIFICATION` remains a valid
classification; the question text is not stored or shown yet, and the column for
it will arrive in the migration that adds the feature.

**Why.** It is explicitly an optional differentiator. Building it before
submission, analysis, review and persistence are finished and tested would risk
the required scope for a secondary feature.

## ADR-014 — Demo identities are not authentication

**Decision.** Votes are keyed by a browser-scoped identifier, and the review
queue is an open route carrying a permanent notice that the environment has no
authentication. No simulated access control is added.

**Why.** A role toggle that protects nothing would be worse than none: it looks
like a security boundary and is not. A unique constraint on
`(request_id, voter_key)` genuinely prevents accidental double voting, and that
is all it is claimed to do.

**What production would require.** Real identity (OIDC/SSO), role-based
authorisation on every mutating endpoint, rate limiting, abuse detection, audit
logging tied to real user ids, and no administrative endpoint exposed without
authorisation. Listed in the README under limitations.

## ADR-015 — Supporting a request is idempotent, not a conflict

**Change of decision.** The Phase 1 plan said a second vote from the same
identity would return `409 Conflict`. It does not. `POST
/api/requests/{id}/votes` returns `201` when the vote is newly recorded and
`200` when this identity had already supported the request. `DELETE` is
idempotent in the same way: withdrawing a vote that is not there returns `200`.

**Why it changed.** Making the conflict an error forced a second response shape
on that endpoint — either a `409` carrying the error envelope and no count, or a
`409` carrying the vote payload, which would mean two different body shapes for
the same status family. Neither is worth it for a toggle button. "I support
this" is a statement of desired state, so the same request twice should produce
the same state and say so.

**What still prevents the duplicate.** `UNIQUE (request_id, voter_key)`, via
`INSERT ... ON CONFLICT DO NOTHING`. The index decides, so two simultaneous
clicks cannot both insert, and the endpoint reports what the database actually
holds.

**Every vote response carries the authoritative count and `has_voted`,**
including the no-op. That is what lets a client whose local state has drifted —
cleared browser storage, a second tab, a double click — correct itself from the
response instead of guessing.

**Cost accepted.** A client cannot distinguish "I just voted" from "I had
already voted" by status code alone. It does not need to: the body says.

## ADR-016 — Search: full-text index first, substring as a fallback

**Decision.** `GET /api/requests?q=` matches with
`search_vector @@ plainto_tsquery('english', $q)` **or** a case-insensitive
substring match on the title and description.

**Why both.** The generated `tsvector` with its GIN index handles word-level and
stemmed matches — searching `reports` finds `report` — which is what makes the
search feel like search rather than string matching. But `plainto_tsquery` does
not match partial words, so typing `spreadsh` would return nothing while the
user is still typing. The substring arms cover that.

**Cost accepted.** The substring arms cannot use the GIN index, so a query that
matches nothing by word still scans the table. At this dataset size that is
irrelevant, and the fix when it stops being irrelevant is a `pg_trgm` GIN index
on the two columns — not a different search engine. Both behaviours are
covered by tests, including one asserting the stemmed match specifically so a
future change to the predicate cannot silently reduce it to substring matching.

**Not done:** ranking by relevance (`ts_rank`). The board sorts by date or by
support count, both of which a product manager can reason about. A relevance
score mixed into that ordering would be a third, unexplainable axis.

**Safety.** The search term reaches PostgreSQL only as a bound parameter, and
the substring match uses `strpos(lower(...), lower($1))` rather than `ILIKE`
with an interpolated pattern — so `%`, `_` and backslashes in user input are
ordinary characters with no escaping to get wrong. The `ORDER BY` clauses are
fixed strings selected by a validated enum; nothing from the request is ever
interpolated into SQL. Tests cover a `DROP TABLE` attempt and pattern
metacharacters.

## ADR-017 — Candidate retrieval uses OR semantics; the board's search does not

**Decision.** The search tool the model calls relaxes the generated tsquery from
AND to OR (`replace(plainto_tsquery(...)::text, '&', '|')`) and orders by
`ts_rank`. The board's user-facing search keeps AND.

**Why.** `plainto_tsquery` builds an AND query. The model searches with the need
it identified — a sentence, such as "send a recurring sales report without
rebuilding it by hand" — so under AND every term would have to be present and
the search returned **nothing**. This was found by a test, not by reasoning: the
fallback path produced "no candidate requests were retrieved" for a request that
had an obvious duplicate sitting in the table.

The two searches have different jobs. Candidate retrieval optimises **recall**,
because the model supplies precision afterwards and a candidate never seen can
never be judged. A person typing two words into the board wants **both** words.
Relaxing the operator on the already-sanitised tsquery keeps the stemming,
stopword handling and escaping that `plainto_tsquery` provides, and `ts_rank`
plus the row limit keep the result set small and ordered.

**Cost accepted.** OR matching is permissive: a long query can touch many rows
before the limit. At this scale that is irrelevant, and the fix when it stops
being irrelevant is a `pg_trgm` index, not a different engine. A regression test
asserts that a sentence-shaped query still retrieves a known duplicate, so this
cannot silently revert to AND.

## ADR-018 — The detail page renders 404 content with a 200 status

**Observed.** `GET /requests/{unknown-id}` in the browser renders the correct
"page could not be found" UI, but the HTTP status is 200. The API's own
`GET /api/requests/{unknown-id}` correctly returns 404 with the project error
shape.

**Why it happens.** The route is partially prerendered: the static shell is sent
before the streamed boundary resolves, so the status line is already committed
by the time `notFound()` runs inside it.

**Decision: accept it and document it.** Removing the prerendered shell for that
route would fix the status and cost the instant-navigation property on a page
that is always dynamic anyway. Nothing in this application reads that status —
the client reads the API's 404, which is correct — so the trade is a real UX
property against a status code no consumer uses.

**When this would be the wrong call.** If the page had to be crawled or
monitored by something that keys on HTTP status, the route would be opted out of
prerendering. That is a one-line change, recorded here so it is a decision
rather than an oversight.

## ADR-019 — A label was corrected; the prompt was not

**What happened.** The first live evaluation run failed one case of six:
`duplicate-different-words`, the "Excel export" versus "scheduled report
delivery" pair. The label said `DUPLICATE`; the model answered `RELATED`.

**Decision: correct the label, leave the system prompt alone.**

**Why the model was right.** Our own system prompt defines the two values:

> `DUPLICATE`: it represents essentially the same need.
> `RELATED`: there is a shared underlying problem, but the requests are not
> interchangeable and could be delivered separately.

An export button and a scheduled email are not interchangeable, and either
could ship without the other. The label contradicted the definition the model
was given. During the end-to-end journey the model made the distinction
unprompted: *"That is a separate deliverable from an export, so I marked them
related rather than duplicate."*

**Why the prompt was not changed.** Making "same need, different deliverable"
a duplicate is a product decision with real consequences — it would push the
system toward consolidating requests that a team would ship separately, and a
false duplicate costs a product manager more than a missed one. Changing it to
make a test pass would have been the worst of both: a product change motivated
by a metric.

**How the change is kept honest.** The dataset is versioned, the label change
carries its justification in `cases.json`, and both runs are preserved in
`backend/evals/RESULTS.md` — v1 at 5/6 with the failure explained, v2 at 6/6.
The model returned the same answer in both, so the difference is **not** a model
improvement, and the documentation says so in those words.

**The real lesson is about the labels, not the model.** One person wrote them,
and that is exactly how the error got in. A measurement anyone should trust
needs several independent labellers and a reported agreement rate; that is
recorded as future work rather than implied to exist.

**Provenance correction.** The Excel-export example comes from our own Signal
product specification, not from the assessment brief. Earlier wording of mine
attributed it to the brief; that was wrong, and the eval dataset now records the
provenance next to the case.
